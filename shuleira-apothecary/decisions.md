# 判断の記録（decisions.md）

work委譲用指示書 v1.1 §06 に基づき、「自分で決めてよいもの」はここに決定と理由を記録し、
「保留にするもの」は暫定対応とあわせてここに記録する。

## 決定事項

### D01. 配置場所を一時的にHunyuan3D-2リポジトリのサブフォルダにした
- **決めたこと**: 専用リポジトリ `eiji-lab/shuleira-apothecary` を新規作成しようとしたが、
  GitHub App連携に `Resource not accessible by integration`（リポジトリ作成権限なし）で失敗。
  作者の判断で、一旦 `Hunyuan3D-2` リポジトリのサブフォルダ `shuleira-apothecary/` に
  自己完結した状態で配置し、既存ブランチ `claude/new-session-h6ewip` 上で開発を続行する。
- **理由**: 作者が翌日から長期間連絡不可のため、リポジトリ作成待ちで停止しないこと優先。
  ディレクトリを自己完結（独自 package.json / node_modules は配下限定）にしておけば、
  後日 `git subtree split` 等で専用リポジトリへ移行するのは容易。
- **帰還後にやること**: `eiji-lab/shuleira-apothecary` を作成し、このフォルダの履歴を移す。

### D02. 技術スタック
- **決めたこと**: TypeScript + Vite（devDependencyとしてのみ使用）。テストは Vitest。
- **理由**: 指示書の制約「CDN依存を作らない。オフラインで完全に動作すること」は
  *本番ビルド後の成果物* に対する制約と解釈した。Viteはビルド時ツールであり、
  `vite build` の出力（`dist/`）は外部リクエストを一切行わない静的HTML/JS/CSSになる。
  素のTSファイルをブラウザに読ませる方式より、バンドル・型チェック・テストの土台が
  短期間で安定して組める点を優先した。

### D03. データの読み込み方式
- **決めたこと**: `materials.json` 等はすべて `src/data/` 配下に置き、
  TypeScript側から `import data from './data/materials.json'` で静的import する。
  実行時の `fetch` は行わない（＝オフライン時にネットワークエラーになる経路を作らない）。
- **理由**: 指示書「コード内に数値・文言をハードコードしないこと」は満たしつつ、
  「CDN依存を作らない。オフラインで完全に動作する」を両立する最も単純な方法。

### D04. localStorage 保存モジュールの分離
- **決めたこと**: `src/state/storage.ts` に読み書きを隔離し、
  ゲーム側は `SaveStore` インターフェース越しにしかアクセスしない。
- **理由**: 指示書「保存処理は薄いモジュールに隔離し、差し替え可能にすること」に対応。
  将来的にIndexedDBや別ストレージに差し替える場合、このファイルだけ差し替えれば済む。

### D05. JSONスキーマ設計（第1段階）
- **薬効軸**: `鎮静/覚醒/鎮痛/解毒/遮断/保持/解熱/浮遊`。強度は 1〜3（＋〜＋＋＋に対応）。
- **副作用軸**: `依存/毒性/鈍麻/混濁/発熱/腐食`。同じく強度 1〜3。
- **特殊素材**の扱い:
  - 04谷水・05霧雫は「希釈用」。効果軸を持たず、`effects: []`。
  - 11濁茸は「他の全薬効を+1段階引き上げる」ため `amplifiesAllEffectsBy: 1` という
    専用フィールドを追加（他の素材にはない）。
  - 21神樹落葉は「全軸+1」のため `effects` に8軸すべて strength:1 を明示的に列挙。
- **在庫層** (`supplyTier`): `常時在庫 / 配給 / 交易入荷 / 密輸` の4種。
  素材一覧の見出し（渓谷産／煙草関連／帝国産／他国産／密輸品）から機械的に対応させた。
- **試作範囲外データも全件残す**: `inPrototypeScope: boolean` を客・症例・助言役の各エントリに
  付与し、指示書「データには全10種・全12症例を入れておくこと」を満たす。表示・出現の
  ON/OFFはこのフラグで制御する（後から有効化できる設計）。

### D06. 例外組み合わせE03（カトレア塩）の扱い
- **決めたこと**: `combos.json` にE03を「予約済み・未実装」として残す
  （`status: "reserved"`, `active: false`）。カトレア塩は現行22素材に含まれないため
  発火しない。素材追加の判断自体は「保留」（下記P03参照）。
- **理由**: 指示書は素材の追加・削除を「保留にするもの」に明記。E03の番号を欠番にせず
  ドキュメントの番号体系をそのまま保持した。

## 保留事項（暫定対応込み）

### P02. 台の傷みの具体的な閾値
- **内容**: 「腐食の副作用がある素材（蝕鱗・灰死粉）を使うと蓄積」「限界に達すると
  その日使用不可」とあるが、具体的な閾値（何回で焦げるか）は未確定。
- **暫定対応**: `progression.json` に `tableDamageThreshold: 3`
  （腐食+1の素材を3回使用、または腐食+2を2回相当で焦げる想定の
  ダメージ蓄積式 `sum(腐食strength) >= 3` で使用不可）を仮設定。
  バランス検証（第4段階）の結果次第で調整可能な数値としてJSON化した。
- **判断が必要な理由**: 数値バランスは「検証結果に基づく限り」自分で決めてよいとされているため
  暫定値を確定値に近い形で設定しつつ、キャラクター/世界観に関わらない純粋な数値として
  このまま実装を進める（＝止まらない）。分類上は「決定事項」寄りだがv1時点の根拠が
  薄いためここに記録。

### P03. オルガの声かけ条件の詳細

### P05. 在庫のリセット方式（日次 or 通し）
- **内容**: 在庫を1日単位でリセットするか、通しで管理するかが未確定。
- **暫定対応**: 「通しで管理」を採用（在庫は日をまたいで持ち越す）。理由: 客の支払いが

  ゲームデザイン上の整合性から選んだが、世界観そのものへの影響はないため本来は
  「決定事項」寄り。念のためここに残し、報告書で最優先確認事項にはしない。
- **判断が必要な理由**: 経済/資源設計の根幹に関わり、後から変更するとバランス調整が
  やり直しになるため、作者確認を推奨する項目として記録。

### D09. 調合ロジックの数値化（第2段階）
素材文書の例外14種・投入順ルールは現象の文章表現のみで、具体的な数式は書かれていない。
「文書に書かれていない細部の挙動」として以下の通り実装した（`src/engine/compound.ts`）。

- **投入順の重み**: 位置 `pos`（0始まり）、総数 `n` として
  - 薬効側 `effectMultiplier = 1 + 0.15 * (n - 1 - pos)`（先に入れるほど強い）
  - 副作用側 `sideEffectMultiplier = max(0.25, 1 - 0.15 * pos)`（後に入れるほど抑えられる）
- **同一素材3つ以上の頭打ち**: その素材の3回目以降の投入は薬効に加算しない
  （occurrenceIndex >= 2 で効果を0扱い）。副作用は常に加算され続ける。
- **濁茸の全薬効+1段階**: 他素材の薬効strengthに+1（`amplifiesAllEffectsBy`の値）を
  加算してから重み付けする。濁茸自身は薬効を持たない。
- **致死判定の閾値**: 副作用「毒性」の合計が6以上で `lethalRisk` フラグが立つ
  （蝕鱗単体3では発火せず、蝕鱗3個投入や強い組み合わせで初めて超える値として選定）。
- **例外14種の個別解釈**（severityラベルと整合するように設計）:
  - E01逆転: 鎮静を0にして同量を覚醒へ付け替え、客が興奮する
  - E02純化: 依存を上限1に抑制
  - E05無効化: 解熱・発熱の両方を0にする（「何も効かない」を全体無効化ではなく
    この2軸の相殺として解釈）
  - E06暴走: 浮遊に+5（天井まで浮く暴走を表現、致死ではない）
  - E07後遺症: 鈍麻の合計を2倍に増幅
  - E08緩和: 発火時、全副作用軸を0.5倍
  - E09被覆: 毒性を上限1に抑制
  - E10根治: `curesAddiction`・`customerCollapsesThatDay`フラグのみ（数値操作は不要、
    症例側のS06根治判定と連動）
  - E11極端例: `beginsTreeification`フラグのみ（症状解消は上位層で扱う）
  - E12最良: 全副作用軸を削除（ゼロ化）
  - E13過剰増幅・致死: 遮断+5, 毒性+5、`lethalRisk`を強制true
  - E14解毒剤: 毒性・腐食を0に固定、E10より穏やかな根治として区別
- **検証**: `tests/engine.test.ts` で31件のテスト（231通りの2素材組み合わせ全数検証、
  例外14種個別、投入順、頭打ち、致死判定、E04即時破壊、症例充足判定）が全てパス。
  数値は仮のバランス値であり、第4段階の自動プレイ結果次第で調整可能（この設計のまま
  係数だけ変えられる）。

### D10. 客の支払い品を素材IDへ対応させた（試作範囲の客のみ）
- **決めたこと**: ハウ→崖苔(M06)、ネル→燼葉(M13)、トビ→羽灰(M09)、オルガ→霧雫(M05)。
  ミルの支払い（きれいな形の石）は`addsToInventory:false`のため在庫加算しない。

### D11. UI実装の技術選定とプレイヤー症状の視覚効果・在庫初期値
- **決めたこと**:
  - フレームワークを使わず素のTypeScript＋DOM文字列レンダリング（毎ティック再構築）を採用。
    状態は`src/state/gameState.ts`の純粋関数群で管理し、`src/main.ts`が唯一のDOM副作用点。
  - 症状演出は企画仕様§04の「揺れ→文字の乱れ→表示食い違い→暴走」をCSSクラス
   （`stage-mild/moderate/severe/critical`）で実装。重度では素材棚の表示ラベルに
    視覚的な「？」を付けるに留め、実際に投入される素材IDは正しいまま
    （＝「見た目は怪しいが実際の間違いはミス率テーブル側で起きる」の分離を維持）。
  - 「掴んだ素材が別のものになる」ミスは`addMaterialToTable`内で
    `progression.json.playerSymptom.mistakeRateByStage`に従い確率発生させ、実際に
    別素材が投入される（表示と実態が食い違う体験を機械的に再現）。
  - 初期在庫は供給層ごとに固定値（常時在庫8・配給4・交易入荷1・密輸0）から開始し、
    以降は在庫を通しで管理する（D05と整合）。具体的な初期値はバランス検証前の暫定値。
  - 動作確認にPlaywright（`playwright-core`、devDependency）を使用し、日開始→客来店→
    素材投入→調合→提供→在庫加算→日終了の一連のフローをChromiumで実地確認した
    （コンソールエラーなし。スクリーンショット確認済み）。
- **既知の簡略化**（report.mdにも記載）:
  - 客の再来・症状悪化の複数日にわたる持ち越し（例: ネルの未処置→S11移行）は
    本試作のゲームループでは未実装（1日ごとに客インスタンスが使い捨てのため）。
  - カイ・サユ・ロゥエン・ダン・名を言わない客の専用UI分岐（型:中間/A→C/躁うつ等）は
    試作範囲外のため未実装。

### D12. 自動プレイ検証で発覚した在庫枯渇バグを修正（常時在庫・配給の日次補充）
- **発覚の経緯**: 第4段階の自動プレイ検証（800日×3方針）を実施したところ、22素材中
  18種がほぼ使われず、特に基本素材（三号草・碧血石など）が序盤で枯渇したまま
  二度と補充されないことが判明した。原因は「在庫を通しで管理する」（D05/P05）を
  文字通り「初日に配ったきり一切補充しない」と実装していたこと。
- **問題点**: 素材文書§08は「常時在庫＝ほぼ切れない」「配給＝量は日ごとに変動」と
  明記しており、これは日次で一定量が供給され続けることを前提とした記述である。
  一度きりの配布では、数百日規模は疎か数日で棚が空になり、仕様の記述と矛盾する。
- **修正内容**: `常時在庫`（基準8個）・`配給`（基準4個）の2層を対象に、
  日の開始時に在庫が基準値を下回っていれば基準値まで補充する処理を追加した
  （前日の残りや客からの支払い分はそのまま活かし、上書きはしない＝
  `Math.max(現在庫, 基準値)`）。`交易入荷`・`密輸`は引き続き補充対象外とし、
  支払いと供給イベント（キャラバン到着・密売人の来訪等）でのみ増える
  （「数が来ない」「極めて不安定」「売人が来た日にしか手に入らない」を維持）。
- **検証**: 修正後に800日×3方針（総接客数9,884件）を再実行し、22素材すべてが
  使用され、判定基準3項目（未使用素材ゼロ／煙草消費が自他に分散／重度到達後の
  成功率低下）を全て満たすことを確認した。詳細は `scripts/balance-report.md`。
- **位置づけ**: 世界観判断ではなく実装バグの修正であるため保留にはせず、
  検証結果に基づいてそのまま修正・前進した（指示書§06「決めてよいもの」に該当）。

### D13. タイポグラフィの作り直し（作者フィードバック対応）
- **経緯**: 帰還後、作者から「デザインがダサい、単純なブラウザゲームに見える」との
  指摘。原因を確認したところ「タイポグラフィ・文字情報」が最も気になる点との
  こと（システムフォント任せで、フォームUIはブラウザ既定のフォントのまま、
  国の空気や台詞の重みを伝える文字設計が何もなかった）。
- **決めたこと**: 企画仕様§01の「文体の切り分け」（棚・器具・手順は淡々と実務的、
  客の台詞と入ってくる客のほうがおかしい）を、そのまま書体の切り分けに対応させた。
  - システム／UI（HUD・ボタン・素材名・タブ）＝ゴシック体 `Zen Kaku Gothic New`
  - 客の台詞・シュレイラの締めの一言・タイトルロゴタイプ＝明朝体 `Shippori Mincho`
  - どちらもOFLライセンスのフォント（Google Fonts配布）。CDNからは読み込まず、
    `scripts/fetch-fonts.sh` で取得した元TTFを `scripts/subset-fonts.py`
    （fontTools使用）でゲーム内実使用文字のみに絞り、woff2として同梱した
    （6ファイル合計 約940KB。元TTF合計 約30MBから大幅に削減）。
    元TTFはリポジトリに含めず、`.gitignore` で除外している。
  - `button/input/select/textarea`に`font-family: inherit`が無く既定のUIフォントに
    なっていたため明示的に継承させた。これが「素のブラウザ感」の主因の一つだった。
